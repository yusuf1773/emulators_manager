# Emulator Manager

Менеджер игр и эмуляторов на C++23. Сейчас интерфейс — CLI; Qt не требуется.

## Структура

```text
app/
  main.cpp
  bootstrap/           создание и связывание зависимостей
  cli/                 команды, разбор аргументов, таблицы
include/emu/
  domain/              Game, Emulator, CommandHistoryEntry
  application/         сценарий запуска и интерфейсы зависимостей
  persistence/         конфигурация и JSON-репозитории
  launch/              стратегия запуска и исполнитель процесса
src/
  application/         реализации сценариев и реестра стратегий
  persistence/         работа с файлами и конфигурацией
  launch/              формирование запроса и запуск процесса
tests/
  unit/                запуск с подставными зависимостями
  integration/         сохранение данных и проверки CLI
cmake/                 подключение внешних зависимостей
```

Заголовки подключаются через `emu/...`; реализации шаблонов остаются в заголовках.
Все типы проекта находятся в пространстве имён `emu`.

## Зависимости и границы

| CMake-цель | Ответственность | Зависимости |
| --- | --- | --- |
| `emu_domain` | Модели данных | Стандартная библиотека |
| `emu_application` | `LaunchGameService`, интерфейсы репозиториев и `ProcessRunner`, реестр стратегий | `emu_domain` |
| `emu_launch` | `DirectLaunchStrategy`, `SystemProcessRunner` | `emu_application` |
| `emu_persistence` | JSON, конфигурация, сохранение | `emu_application`, nlohmann/json |
| `emu_manager` | CLI и создание зависимостей | Модули выше, CLI11 |

`LaunchGameService` находит игру и эмулятор, выбирает стратегию, получает
`LaunchRequest` и передаёт его `ProcessRunner`. Стратегия формирует аргументы,
но сама процесс не создаёт. В тестах исполнитель только записывает запрос.
Команды добавления и просмотра работают через `Repository<T>`; JSON-реализацию
выбирает `app/bootstrap`. При появлении дополнительных бизнес-правил для этих
операций их следует вынести в отдельные application-сервисы.

Для нового интерфейса нужно собрать те же зависимости и вызывать core.
Зависимости на CLI11, JSON и будущий Qt нельзя добавлять в domain/application.

## Сборка и тесты

Нужны CMake 3.20+ и компилятор со стандартной библиотекой, поддерживающей
используемые возможности C++23: ranges, `std::format`, часовые пояса chrono.
Локальная проверка выполнена на GCC 15.2 и CMake 4.2.3.

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --parallel
ctest --test-dir build --output-on-failure
./build/emu_manager --help
```

Версии зависимостей сохранены: CLI11 2.5.0 и nlohmann/json 3.12.0.
CMake сначала ищет эти версии среди установленных пакетов, затем использует
FetchContent. Для CLI11 закреплён commit, для JSON — SHA-256 архива.
Первой сборке может понадобиться интернет. Для существующих локальных исходников
поддерживаются `FETCHCONTENT_SOURCE_DIR_CLI11` и `FETCHCONTENT_SOURCE_DIR_JSON`.

Сборка и тестирование core без загрузки CLI11 и JSON:

```sh
cmake -S . -B build-core -DEMU_BUILD_CLI=OFF -DEMU_BUILD_PERSISTENCE=OFF
cmake --build build-core --parallel
ctest --test-dir build-core --output-on-failure
```

Тесты проверяют выбор игры/эмулятора/стратегии, регистрацию и поиск стратегий,
формирование запроса запуска, порядок аргументов, передачу ошибок, создание и
чтение конфигурации, сохранение JSON, безопасную замену, лимиты истории и команды CLI.
Заголовки domain/application дополнительно компилируются каждый отдельно без
внешних библиотек. Тесты используют временные данные и не запускают эмуляторы.

## Совместимость

Сохранены имена CLI-команд и поля JSON. Имена игр и эмуляторов пока служат ключами.
Конфигурация читается из `config/config.json` относительно рабочей директории;
пути в конфигурации разрешаются относительно её каталога.

Исправлены сохранение `--repl`, потеря записи при конфликте `replace-*`, код
завершения при ошибке аргументов и обработка нулевого лимита истории. Нулевой лимит
отключает историю и очищает сохранённые записи; уменьшение лимита оставляет самые
новые. Файлы репозиториев заменяются после полной записи временного файла,
состояние в памяти обновляется только после успешного сохранения. Одновременное
редактирование данных несколькими процессами не поддерживается; гарантии
восстановления после отключения питания не заявляются.

`SystemProcessRunner` сохраняет прежний запуск через `std::system` и правила
кавычек исходного проекта, ориентированные на Windows. Это адаптер совместимости:
он не гарантирует переносимость запуска и безопасную обработку произвольных
shell-символов. До реального использования с эмуляторами его следует заменить
исполнителем без shell и проверить на целевой ОС. Проверка Windows в эту итерацию
не входит. `LaunchProfile`, рабочая директория запуска и SQLite — следующие этапы.

## Стиль

Форматирование и именование основаны на [Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html):
файлы `.h`/`.cpp`, `#pragma once`, приватные поля с `_`. По правилам проекта
отступы делаются табами шириной четыре символа. Конфигурация `.clang-format`
основана на Google и содержит это локальное отклонение; проверена clang-format 18.1.8.
Комментарии в коде не используются. Существующие C++23 и модель ошибок через
исключения сохранены: переход на другой стандарт или контракт ошибок не входит
в этот рефакторинг.
